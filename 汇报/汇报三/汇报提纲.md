### P01｜封面：ModelRouter — 面向真实多 Agent 任务的动态模型与推理档位路由

### P02｜研究动机：单次请求便宜 ≠ 整个任务划算
- **要讲**：静态能力与价格排名可以指导选模型，却无法说明在代码修复、测试/失败恢复与多 Agent 交接时，最终任务成功率和全部费用会怎样。

### P03｜研究场景：一个多 Agent 任务中到底在发生什么？
- **情景示例**：同一软件问题：Planner 规划 → Coder 定位/修改 → Tester 验证 → 若失败则 Recovery 继续修复；真实 Harness 才能决定是否存在这些角色，不把示例当所有任务的固定拓扑。
- **核心变量**：当前 \`agent_id\`、\`agent_role\`、\`subtask_goal\`、\`task_phase\`、已发生的 handoff/失败、剩余预算；角色是任务信息，不代表事前绑定模型。
- **视觉**：四个角色、共享任务目标、执行反馈箭头，显示某一时刻当前子 Agent 被高亮；**AI 生图素材 ②** 仅做角色与协作的插画，节点名称和箭头由后期矢量/文本加上。
- **讲法**：「不同角色的工作内容不一样；我们要检验这种差异是否值得改变 Model×Effort 的选择。」
- **警告**：SWE-bench Verified 本身是软件任务 Benchmark，**不天然自带多 Agent 分工**；多 Agent 由所选可复现 Harness 提供。

### P05｜**核心方法主图（论文 Fig.2；整页重点，建议讲 100 秒）**
- **目标**：让导师直观看明白「一个 Router 接收 Agent 信息，对树形合法候选打分，同时决定模型和该模型的原生 Effort，并随执行反馈再次决定」。
- **严格画成如下 7 个区域，从左到右/上下组织**：
  1. **Task / Multi-Agent Runtime（左上）**：原始 Task → 当前执行的子 Agent（\`agent_id\`、\`agent_role\`）→ \`subtask_goal\`、\`task_phase\`、已发生 handoff/工具/验证；允许 Planner/Coder/Tester/Recovery 角色按 Harness 变化。这里的 Agent 流程是**被观察/接入**的，不是 Router 创建的新 Agent 。
  2. **Decision-time State（左下）**：三个抽象信息组：**T Task & Agent Needs**（当前任务/角色/子任务）、**M Candidate Capability & Economics**（具体候选的能力/费用）、**H History & Continuity**（Context/KV/此前 Trace/已见 Verifier/预算余量）。T/M/H 是实验信息组，不是需要监控的全部字段。Provider availability/context/tool/privacy/budget hard limits 是合法性条件。
  3. **Model Registry / Tree（中央上）**：模型身份树，示意 Model A → {Low,Medium,High}，Model B → {Default,High}，Model C → {Default}（只是结构示例，**不得暗示真实某厂商具体支持这些档位**）。每个模型挂 Provider、能力、价格、缓存规则与原生 Effort 支持。**K = 模型身份数量，不是叶子/动作数**。
  4. **Legal Action Filter（中央）**：当前可用/工具能力/上下文窗口/合法 effort/隐私/预算/安全会话连续性先过滤。输出可变长 \`A_t={(m,e) | legal(m,e,s_t)}\`；不能把非法调用交给模型学习排除。
  5. **Single Shared Candidate-Conditioned Router（核心突出）**：输入 \`s_t\` 和每个合法 \`(m,e)\` 的特征 \`phi(m,e,s_t)\`，使用同一评分机制 \`q_theta(s_t,m,e,phi)\` 得到各候选分数；择一 \`a_t=(m*,e*)\`。**这不是 Model→Effort 的两个独立路由器，也不是预设固定 3–5 个 combo 类别**。
  6. **Agent Executor（右侧）**：只把选定的模型和原生 Effort 用于**当前**子 Agent 的下一次合法模型调用；Agent 继续自己负责工具调用和任务执行。记录 Model、Effort、真实 token/缓存、API/本地成本。
  7. **Outcome & Feedback Loop（右下回环）**：实际工具结果、验证失败、真实 usage/cached tokens、Trace 更新下一次 \`s_{t+1}\`；直到终局输出 \`resolved\`、完整 Episode USD、latency。终局标签只在执行后用于评价/学习，**不能前向泄漏**。
- **必须画出的箭头**：Runtime → State；Model Registry → Legal Filter；State + Legal Actions → Shared Router；Select → Agent Executor；Executor → Observed Feedback → State（回环）；终止时 → Episode Evaluator/Ledger。
- **必须避免**：跨模型/Provider 物理 KV 直接迁移箭头；提前看到最终 resolved；让 Router 决定子 Agent 拓扑；把 Agent role=user/assistant/tool 当成实际子代理角色；把模型与 Effort 画成彼此独立且各自有不同 Router 的两棵树。
- **建议主图标题**：**One Router, Variable Model–Effort Actions, Runtime Agent Feedback**。
- **制作方式**：**精确的矢量流程图（SVG/PowerPoint Shapes/tldraw）而非纯 AI 生图**。可以生成底纹/背景，但所有中文标签、动作树、箭头和公式应后期精确可编辑制作。
- **论文与 PPT 的区别**：论文版本可展开更多字段；PPT 只保留 T/M/H 三组和模型树，详细字段写讲稿或备用页。

### P06｜实验怎么公平比较？Benchmark、模型池与 Baselines
- **同一横向对照条件**：同任务 ID/原始仓库、同 Harness、同工具/Verifier、同模型身份池、各模型真实 Native Effort、可比预算、同费用账本；开发集选池/阈值，独立任务只用于最后测试。
- **Benchmark 候选（按照文档，不冒充都已可用）**：
  - **首选 Coding**：SWE-bench Verified + 可重复多 Agent Harness；它是任务/终局评价器，是否满足多角色依赖于 Harness。
  - **Agent 路由参考/适配**：TwinRouterBench 的可用动态 Agent 路由设置及实际算法，需核代码/任务映射；不能用 Benchmark 名称冒充算法名。
  - **补充任务**：Terminal-Bench 2.1 / External DEV 如符合任务类型和许可可作为相关验证，但现有封存评测集**不能擅自训练、提前读取或当已完成评测**。
  - **跨任务类型（RQ5 必需但尚待确认）**：Research/Data 等有真实多 Agent 角色、统一可执行终局评价的 Task+Harness 才能加入；没有可用来源时优先 Coding 内部预定义任务族/规模/协作结构。
  - **RQ4 消融数据来源**：既有合规 S1 偏好、S2 Agent 轨迹、S3 缓存辅助与 Laya/Kev 训练记录；CooperBench 等角色轨迹只在训练准入和实际编码确认后作为可选状态输入，不是独立跨角色互补性 RQ，也不等于最佳 Model×Effort 真值。
- **基线分层**：
  - Fixed：Always-Strong、Always-Cheap、Best-Fixed-on-Dev、**Role-Static**（开发集为各角色选固定配置）。
  - Mix：**Random Whole-Episode Mix**（固定模型策略的整任务混合/包络，不是每步随机）。
  - Simple Dynamic：Task-only、Per-call Greedy、Rule/Sticky。
  - Learned/Existing：同一 Harness 真正接入的已有 Agent Router 算法，如 TwinRouterBench 提供的具体 adapter、MasRouter/ProgRouter 的可比路由子机制；不可把不同系统原论文数字直接并到主表。
  - Ours：Full ModelRouter。
- **排版**：上半 T2 Benchmark/评测协议空白精简表，下半基线分组矩阵；旁注「同池、同 Harness、同终局」。
- **指标**：成功率、平均完整 Episode USD、Cost/Resolved、真实 Router Overhead、P95 任务耗时；失败、重试、缓存真实计价均纳入 Episode。

### P07｜RQ1-A：整个 Router 到底有没有优势？
- **科学问题**：与固定、角色静态、随机整任务混合、简单动态、可比学术 Router 运行同一真实任务后，Full 能否在 Success–Episode USD 平面上形成更优非支配点？
- **Fig.3（最终论文主结果图）**：X=Mean Complete Episode USD ↓；Y=Task Success Rate ↑；点/不同预算阈值对应策略配置；标出实测固定策略/随机整任务混合包络、Full 和同 Harness 学术 Router。
- **不能做**：提前生成“Full 在最左上”的趋势线；用 AA 静态能力当 Y；只在成功任务上算平均费用；不同 Harness 的成本数字直接横排。
- **配 T3**：Policy / Success / Mean Episode USD / Cost per Resolved / P95 / Router Overhead / CI；每格数字待测。
- **讲给导师**：「如果我们连一个设计得好的 Role-static 或两模型 Episode 随机混合都赢不了，就不能说明复杂动态 Router 值得。」

### P09｜RQ2：模型池放哪些模型、几个模型？
- **变量定义**：**K=模型身份数**（一级节点）；每模型有真实支持的原生 Effort 叶子，另记 \`Σ_m |E_m|\` 合法动作数（随时刻合法性可能变化）。
- **实验 A 同 K 比成员**：公开 AA 静态前沿池、Agent dev 选择池、价格分层池、互补池、随机池；Router、G、任务及预算固定。
- **实验 B 比不同 K**：候选 K=3/5/8（仅示意、未批准具体 K），与“前沿外模型加入后边际收益”；不能同时偷偷换算法。
- **Fig.5**：左面板 同 K 不同 pool 的 Success–Episode USD；右面板 X=K，Y=新增模型的任务级净收益或费用差，标注合法动作数。K 不是 Total M×E Actions。
- **配 T6**：Pool Rule、K、真实模型 ID、Legal M×E Count、Success、Episode USD、Marginal Value。
- **讲给导师**：「不是模型越多越好；我们要检验互补模型能不能创造新的路由空间。」

### P10｜RQ3：固定模型池，任务拆成多细比较划算？
- **实验前提**：**固定相同 K、具体模型身份、每个模型的原生 Effort 菜单、同 Router**；同原始任务，预定义可执行的 G 粒度（整体/阶段/细粒度）。
- **对照**：每个 G 下比较 Role-static 或固定与 Full Router；Agent 数、handoff、可用决策边界 F、上下文复制、Trace **如实记录**。G 改变自然导致 Agent 数/F 变化时，这是“整个拆分方案”的效果，不能声称只有 G 单独变化。
- **跨任务类型**：在每个真正可运行的 Task+Harness 内做配对；类型之间先分面展示，不能直接把不同 benchmark 的 raw success 当可比难度。
- **Fig.6**：X=G0/G1/G2（名称和真实实现待定），上面板 Y=Success Rate，下面板 Y=Mean Episode USD；图例 Role-static/Full，分面任务类别；辅助注释 Agents/Handoffs/Trace。
- **配 T7**：Task Type / G / Policy / Agent Count / Handoff / F / Success / Episode USD。
- **讲给导师**：「拆细有利于匹配便宜模型，但会增加交接和上下文成本；两者谁占优势要实测。」

### P11｜RQ4：系统消融——Router 的哪些设计真正有效？
- **问题**：在相同原始任务、真实合法模型池、原生 Effort 支持、Harness 和费用口径下，动作结构、输入状态以及合法训练数据/监督配置各自贡献多少任务级经济收益？
- **Fig.7 三面板**：
  1. **动作设计**：Fixed M+E、Model-only、Effort-only、Hierarchical M→E、Joint M×Native Effort；观察真实成功率/完整 Episode USD，说明行动空间差异。
  2. **变量信息**：T（任务及可选 Agent 子任务）、M（候选经济特征）、H（上下文、实际 KV、Trace、Verifier）的 T/M/H 单组、双组、三组组合；合法动作及权限硬约束永不删除。
  3. **训练数据/监督**：合规 S1、S1+S2、S1+S3、S1+S2+S3，及选定 Laya/Kev Checkpoint/训练对照；缺乏真实联合覆盖或训练证据的组合不得当作已完成。
- **对应表**：T4（输入组）、T5（Model×Effort）、T8（监督/训练数据）；T11 保留训练验证记录；T10 作为共用费用账本。
- **负结果和限制**：未选候选的真值不可由异构历史轨迹生成；已经测试而无收益的特征要记录，不得事后删实验掩饰。
- **一句话**：「让我们知道 Router 的收益到底来自哪个设计，而不是只看到最终模型效果。」

### P12｜RQ5：哪些工作负载值得动态路由，哪些不值得？
- **固定**：已确定的 Router、模型身份池、Native Effort 支持、可比 G/执行协议。
- **预先定义分层**：任务开始前可见的 task type、初始代码仓库/任务规模线索、事先确定的 Agent 角色/依赖结构、预算档位。**实际最终 Trace、最终失败次数、总费用不是决策前“已知难度”。**

## E. 开会时可以直接讲的 70–90 秒简短版本

> 我们现在研究的是长程 Agent 工作流的动态模型路由。和只给一条提问选择大模型不同，Agent 在规划、编码、验证和失败恢复时会不断调用模型。我们先建立一个模型池，每个模型下面保留自己真实支持的推理档位；Router 根据当前哪个子 Agent 正在做什么、已有执行反馈、上下文和成本，联合选择下一次调用的 Model 和 Native Effort。
>
> 论文准备分五个问题。第一，和已有 Agent Router 以及固定、按角色固定（如果场景有这些角色）、随机整任务混合等强基线横向比较，看完整任务成功率和总费用。第二，研究模型池应该选哪些模型、多少个。第三，在同样模型池下，任务拆成多细更划算。第四，把完整的方法消融作为独立 RQ，检验 Model×原生 Effort 联合动作、不同决策状态信息和训练数据/监督配置究竟有哪些价值。第五，检验哪些 Agent 任务有动态路由净收益，哪些任务简单策略就足够。
>
> 目前我们已有多源数据和离线训练基础，但需要把真实子 Agent 角色输入与端到端评测做好。希望今天主要请您帮助确认 Benchmark/Harness、模型池的实际范围，以及最后两个 RQ 的实验可行性。
