## 3. 页面说明

### P16 · 真实三类型决策演示

左栏是「场景与输入」，按卡片格式化呈现：

- **6 个中文预设**：软件缺陷修复、模型 × 推理档位、生产故障处置、多智能体协作、
  长文档理解、代码审查。
- **随机生成一个示例**：从任务域、故障现象、考察动作、选项组、评分等级里随机组合，
  每次点都不一样，适合面试现场临时出题。
- **本次输入**：四个指标（步骤 / 上下文 / 工具调用 / 错误信号）+ 任务域标签 +
  中文任务描述 + 三个问题（选择、评分、判断）及其候选项。
- 「编辑本次输入」可展开完整表单，改完点「应用修改」即可再跑。
- 按钮：`运行 Laya` / `运行 Kev` / `双模型对比`。

中/右两栏分别是 Laya 与 Kev 的结果卡，每张卡三块：

1. **选择 / Choice**：选中项大字 + 百分比，下方三候选完整概率条。
2. **难度 / Score**：期望等级（如 3.18 / 4）+ 中文等级名，下方五档分布。
3. **判断 / Noul**：为真的概率 + 「是 / 否」判定 + 0.5 阈值线。

底部一行：两侧耗时、检查点、是否回退、完成时间；右侧「原始数据」可看本次真实
Request / Response 原文。

### P17 · 同一输入，两种决策

自动读取 `双模型对比` 写入的**同一轮**结果（同一 `test_id`），分四段：

1. **选择结果对比**：三候选并排，每个候选内 Laya / Kev 各一条概率条与百分比，
   被选中的候选会打上对应模型标记。
2. **难度评分对比**：五档等级逐行对比，带两侧百分比；右侧是期望等级与中文等级名，
   以及两者差值。
3. **真假判断对比**：两行概率条 + 0.5 阈值线 + 判定标签。
4. **部署与架构差异**：本次耗时、检查点、架构说明。

「重新比较」会用**同一份输入**再发一轮，整轮替换而不是混轮。

## 4. 请求契约（实测）

```json
{
  "router_family": "laya | kev",
  "state": { "task_domain": "软件工程", "step_index": 3, "context_chars": 1240,
             "prior_tool_calls_count": 2, "prior_error_signals_count": 1, "prompt": "……" },
  "questions": {
    "q_choice": { "type": "choice", "instructions": "……",
                  "criteria": { "cheap_fast": "轻量快速：……", "mid_balanced": "……" } },
    "q_score":  { "type": "score", "instructions": "……",
                  "criteria": ["很简单", "较简单", "中等", "较困难", "非常困难"] },
    "q_noul":   { "type": "noul", "instructions": "……" }
  }
}
```

要点：`choice.criteria` 必须是 **对象**（选项键 → 中文描述），`score.criteria` 必须是
**数组**（等级名，从低到高）。这是 Kev 侧 TypeSafe `SystemOneRequest` 的强校验，
Laya 侧同样形状可用，因此两页共用一份请求体。

> 选项键保留英文短标识（`cheap_fast` 等），页面展示时映射为中文标签
> （轻量快速 / 均衡中档 / 旗舰深度……）。这样既能被模型正确理解，面试时又是中文阅读。

## 6. 科学解释边界（P17 已写明）

- 同一输入下两种架构可能选到同一选项，却给出不同概率分布；本次实测既有「同选不同分布」，
  也有「各选不同项」。
- 难度评分（期望等级）与真假判断（P(真)）是**不同指标**，不能相加、相减或互换。
- 耗时只代表本次部署环境与本次请求，不构成性能基准。
- 一次演示不能证明任一模型在独立测试集上更准确。
- 模型自报置信度不等于真实任务成功率。
