① KV Cache 原理：多层网络下，缓存的到底是什么

一次 prefill 会给每一层的每个注意力头、每个 token 算出一对 K 和 V 并留下来。Query 是临时的，算完就扔，所以它叫 KV Cache。生成第 n 个 token 时，只需要算这一个 token 的 K 和 V，前面 n−1 个直接从缓存里读。

② 多 Agent 的共享前缀：能不能复用同一份 KV Cache？

能不能复用，取决于三件事。前缀是不是逐 token 对齐，推理框架有没有开前缀缓存，多个 Agent 是不是用同一套系统提示词和工具定义。
默认情况 · 独立推理

各自算一遍，显存里存两份一样的

Agent 推理时会把完整上下文提交给推理引擎，引擎为这次请求单独分配一份 KV Cache，逐层记下每个 token 的 K 和 V。默认规则下两个 Agent 的请求互不相干，系统提示词一模一样，引擎也会分别算两遍，显存里就存了两份完全相同的 KV Cache。这是最常见的缓存浪费，默认答案是不能。

开启前缀缓存

RadixAttention：相同前缀只算一次

推理框架提供了前缀缓存开关，RadixAttention 是其中一个。它用一棵 Radix 树按 token 序列索引算过的 KV 块，新请求沿树走，吃到最长的一段匹配前缀，只有真正新增的后缀才计算。高并发多 Agent 的场景特别有用，不然每个 Agent 都要把同一套系统提示词和工具定义重算一遍。

语义缓存 · 注意区分

它复用答案，KV 并没有共享

再往上一层是语义缓存。缓存层把历史问答对按语义相似度建索引，新请求先查语义缓存，命中就直接返回结果，不命中才走推理。它复用的是结果，KV 并没有共享。很多讲解把这两件事放在一起说，概念是混的。真正的 KV 级共享只有前缀缓存。

2在真实链路里，这段共享前缀有多大

真实项目会统一系统提示词和工具 schema，让所有 Agent 共用同一套前缀，引擎用 Radix 树管理这段共享前缀的 KV，相同部分只算一次。链路上每个 Agent 真正属于自己的，只有末尾几百个 token。

坑在哪。如果没做前缀对齐，比如每个 Agent 的系统提示词顺序不一样，工具定义的格式不一样，命中率会直接归零，等于白开。多 Agent 协作和批量任务处理时最容易踩到。
回答能不能共享时，标准思路是先分情况。
  1. prompt 前缀是否对齐（逐 token、字节级一致）
  2. 推理框架有没有开启前缀缓存（RadixAttention / vLLM automatic prefix caching）
  3. 多个 Agent 有没有共用同一套系统提示词和工具定义

连回我们的研究问题。这块巨大前缀同时也是最脆弱的东西，它要求字节级对齐，而路由动作（换模型、换推理档位、换工具集）恰恰要改写这段前缀。所以 路由与缓存命中天然冲突，选择哪个配置，影响的是整条轨迹的缓存状态和成本。
口径。命中价按 Anthropic prompt caching 文档，缓存读是标准输入价的 10%，5 分钟 TTL 写入加 25%，1 小时 TTL 加 100%；OpenAI cached input 是 50%，最小 1,024 token。命中判定要求字节级一致，改一个字符，其后整段失效。
视频里有一处说法要修正。「前缀没对齐会比不开缓存还慢」夸大了。SGLang 的消融实验测出 cache miss 时没有可测量的开销，作者因此把前缀缓存默认常开。准确的说法是收益归零，不是更慢。
