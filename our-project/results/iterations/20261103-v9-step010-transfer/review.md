## 5. 实际研究结果

### 5.1 Val口径与退化

原固定S1共561条，全部来源`ROUTE-004` Arena人类两候选偏好，候选模型并不固定为Sol/Luna。它不是当前一步Verifier成功率，也不是完整Agent成功率。原Trainer的`_load_named_groups`只变换Train，不变换Val；`_evaluate`用单位温度。

| 相同权重的评价口径 | 009 Acc / Loss / Brier / ECE | 010 Acc / Loss / Brier / ECE |
|---|---|---|
| 原S1输入、原Trainer单位温度、FP32 | .6881 / .6361 / .4273 / .0883 | .6720 / .6652 / .4382 / .1171 |
| Serving序列化输入、原Trainer单位温度、FP32 | .5793 / .7290 / .5204 / .1388 | .5526 / .7791 / .5555 / .1598 |
| Serving序列化输入、保存的choice:2温度1.906356、FP32 | .5793 / .6795 / .4862 / .0544 | .5526 / .7007 / .5052 / .0726 |

最后一行复现010旧记录的Acc .5526、Brier .5052、平均置信度.6252，Loss/ECE仅相差.0001。旧009记录则与第一行接近；其旧387/561和本次386/561相差一条近界样本。原旧临时执行脚本已不在项目中，因此不声称找回了该脚本；源码及同权重输入/温度对照已明确证明，旧两组数不能作为同口径差值。

统一原口径后，009至010减少9个正确选择，仍有真实退化，幅度约1.61个百分点。不能继续把旧13.72个百分点差异全归给训练。温度只影响置信分数，不解释argmax翻转。

原Val选择位置0/1由257/304变为266/295。位置不是统一模型ID，不能把此变化称为Sol全局偏置。

### 5.2 20/20与pipdeptree

当前20条来自17个任务：质量14条为Sol9/Luna5；费用6条全部Luna。整体标签是Sol9/Luna11，绝非Sol类别占多数。

009对相同20状态19/20、010为20/20，唯一训练动作翻转是tinydb费用状态从错误Sol改为Luna；两权重在14条质量训练状态均正确。训练Sol选择数反而从10降为9。Sol分数11条上升、9条下降，不支持“所有状态统一推向Sol”的解释。

pipdeptree Sol分数从.0791变为.6301。010 Encoder配009其余组件仍为.6244、选择错误Sol；009 Encoder配010其余组件为.0627、仍正确Luna。四个组合的原S1准确率和pipdeptree动作主要随Encoder变化。其余组件影响置信、Loss与校准，但未恢复010 Encoder的费用选择。

这是表示更新参与遗忘的组件证据，不是已定位某一神经元或已证明某个单独样本造成退化。mpmath Sol分数反而从.1021降至.0384，继续选错；PlasmaPy正确在009中已有，010没有新增跨任务质量正确数。

records、async-timeout、schema各有两行。同任务不能算两项独立泛化证据；records两行原消息相同，分别来自质量与费用比较、赢家均Luna，状态元数据不同。没有将这些原合法比较删除，也没有把它们计成新增任务。tinydb两条是不同故障任务、同一仓库，仓库泛化也不能按两仓库计数。

Moto/Tox原资格L2，不能称祖先未见；Qiskit为L3候选，实际25%成员未知；mpmath、pipdeptree、PlasmaPy有L4及显式STEP排除依据。Vetiver在010之前未见，010之后已参与梯度。早期TRA-002样本的祖先具体成员未在本轮建立，只能明确它们已进入此前STEP材料。

### 5.3 在线语义与Context改动

八个动作前状态实际依次是：初始探索、读CSV后探索、Python命令不可用、NumPy缺失、恢复诊断、依赖安装超时、Python失败但R可用、R工件写入后。最后一种是数据任务产物写入，不等同软件仓库源码修改。离线当前Train以Verify和诊断后Modify为主，Inspect正式一步质量标签仍为0。

真实Python/R组合命令先报`ModuleNotFoundError`，后面的R命令成功使整体退出码为0。旧代码把所有第二步后的成功命令标为Modify，并仅在非零退出码时优先保留错误文本。它们混淆了退出码、环境恢复和源码修改。

在原`v9/runtime/context.py`完成三个小改动：

- 长命令摘要仍为256字符，保留头126字符、分隔5字符、尾125字符；两个heredoc的末尾执行命令现在可见。
- 错误文本选择不再依赖整体非零退出码，组合命令中的真实错误可保留；原退出码、命令及动作后输出不改。
- 成功命令不再仅凭步数归类Modify；已有显式写入命令归Modify、读取归Inspect、真实错误归Recover。该字段仍是命令启发式，不声称由它得到了完整工作树或任意脚本的实际修改内容。

任务/工具预算仍为6000字符，没有未来反馈、参考修复或动作后候选测试进入动作前输入。第六个完成动作后的状态从Modify变为Recover，准确表达Python依赖仍缺失；最新工具输出的错误行可见。

009/010有效重放16个原状态，最终选择全部保持原样：009八次Sol；010六次Sol、两次Luna。长命令、阶段、错误文本分开对照均没有动作改善。原B17闭环八次Sol的质量真值仍未知，不把固定Luna整局成功算为这八个状态的Luna一步优势。

首次重放误加一个没有正式序列化用途的`router_tool_chars`字段，20次前向无效；已移除，仅重做受影响的20次，失效结果不进入科研结论。完整记录中的费用与次数包含该诊断消耗，不伪装零耗时。

### 5.4 质量关系、执行与最终动作

保存的A/B/C/D结果按三个轴分开：关系是否正确、动作是否正确、动作能否执行。B17在pipdeptree错误预测Luna独过，却碰巧选对低费Luna；在ro-crate的原小样本分析可正确预测Sol独过并选择Sol。C留出ro-crate预测双方失败，真实Sol17/17；D留出Build后没有`NO_LOCAL_IMPROVEMENT`训练类别，错误预测Sol局部优势。原相似状态距离只是相关证据，不单独证明错误原因。

ro-crate、Vetiver、Copier的Luna都实际生成`apply_patch`命令，原容器没有该程序，退出127、业务源码没有修改。这是所给bash工具环境中可信的一步执行失败，不能据此评价未实际应用的补丁内容。没有向容器安装额外工具、改原Verifier或替模型执行另一种命令。

Stingray双未完成但Sol修复F2P8集合严格包含Luna2、无新增P2P回归；Build双无局部改善；pipdeptree双方原验证27/27，费用决定赢家，但初始局部ID关系未知；Cogent3双方UNKNOWN。这些旧事实保留，没有强行追加正式赢家，局部监督仍未得到新的可靠独立改善。

## 6. 独立科研判断

明确实现问题是状态摘要和阶段启发式；明确报告问题是Val的输入/温度口径不同；明确模型现象是Encoder更新伴随训练拟合改善、原S1小幅退化和独立费用选择遗失。小样本重复、语义混合与阶段集中均有数据依据，但本轮不能单独证明它们各自的因果份额。

“只有20条也全对”不是研究终点。更丰富摘要、组件交换、正确的费用动作或一条局部优势都不能替代稳定的未见任务质量关系与完整收益。本轮没有证明跨任务动态收益，也没有宣称该研究技术不可行。

## 7. 通俗解释

Router记住了20条题目的答案，但处理新题时的内部表示也变了：训练里便宜Luna的那道题学对了，另一道没训练过的便宜Luna题反而选错。旧报告还拿两种不同的输入和分数口径比较，把退化显得更大。本次把这些现象分开，补回长命令和真实错误，但还没有证明Router能在新任务稳定选择正确模型，更没有证明整局省钱。
